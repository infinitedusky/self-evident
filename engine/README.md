# Self Evident engine

The core: **idea → plan → task → phase → step.** A plan is tasks in order. A task is authored: a title and a brief.
Phases are the atomic unit the engine runs: one agent, one worktree, one commit, each declaring its files and what it
depends on. They are generated by the planner from the task's brief (a person may write them too). Steps are the
builder's own todo list while it builds a phase, captured live. The engine runs every phase whose dependencies are
done, in parallel across all running plans; task order is an implicit dependency; phases that share a file take
turns. Plans land into their own branch and become one PR each.

Founding rule (SHAPE.md): **git holds code, Postgres holds state, this server is the single writer.** The CLI, the
UI and the VS Code view are clients; agents report events, they never write status.

## Run it

From the repo root, one command:

```bash
pnpm install
pnpm dev        # Postgres 17 (docker compose, localhost:5433) + the engine on :4000 + the UI with live reload on http://localhost:5180
pnpm start      # or: the engine alone on http://localhost:4000, serving the built UI (`pnpm build` first)
```

Migrations run when the engine boots. The API is under `/api` (`GET /api` lists the routes); the UI is served at `/`.
## From Claude Code (VS Code or the terminal)

The engine is also an MCP server, one per app, with the same tools as the agent in the web UI: what needs you
(`now`), projects and their graphs, plan a task, start, pause, retry, to-dos and their checklists, the backlog. In a
checkout of the app's repo:

```bash
pnpm --dir <self-evident>/engine se connect .      # prints the one command to run, e.g.
claude mcp add --scope local --transport http self-evident http://localhost:4000/api/mcp/app_…
```

Local scope keeps it to you and that repo; nothing is written into the repo. Then ask Claude Code "what needs me?".
The web UI stays useful for watching (the graph, a project, the to-do lists); nothing waits on it.

In here, `pnpm serve` runs just the engine and `pnpm se …` is the CLI (against `ENGINE_URL`, default `http://localhost:4000/api`):

```bash
pnpm se workspace "My workspace"            # → {"id":"ws_…"}
pnpm se app "Homework Gate" -w ws_…          # → {"id":"app_…"}
pnpm se project create -a app_… -t "The gate" -f examples/demo-plan.json   # tasks in order, each with phases
pnpm se project tick plan_… -r 2               # one dispatch pass with 2 free slots (drafts)
pnpm se project graph plan_…                   # tasks, phases, edges, why each held phase waits, steps
pnpm se phase status ph_… done              # drive a draft by hand, or:
pnpm se watch -p plan_…                     # replay the plan's events, then follow live
pnpm se task plan task_…                    # the planner: brief → phases, decisions, questions (minutes; read-only on the repo)
pnpm se task phases task_… -f phases.json   # or write a task's phases by hand
pnpm se question answer q_… "Yes"           # answer one of the planner's questions
```

A plan file is `[{title, brief?, phases?: [{key, title, brief?, dependsOn?, files?}]}]`: tasks in order.

To run a plan for real, the app needs a repo with a local main checkout and a test command:

```bash
pnpm se app "Homework Gate" -w ws_… --test-cmd "/abs/path/to/.venv/bin/python -m pytest -q poc" --max-budget-usd 10
pnpm se repo infinitedusky/homework-gate -a app_… -p /abs/path/to/homework-gate
pnpm se project create -a app_… -t "Health endpoint" -f examples/homework-gate-health.json
pnpm se project start plan_…                   # integration branch, worktree per task, agent run, landing, PR
```

Each phase gets `<repo>-worktrees/<plan>--<n>` on branch `phase/<plan>/<n>`, cut from `plan/<plan>` (itself cut from
the default branch). A phase in a later task starts only after every phase of the earlier tasks has landed. The agent works there with tools confined to the worktree (no branch changes, pushes or PRs),
commits, and summarises. Landing is serialized per plan: merge the integration branch in → run the test command on
the merged commit → fast-forward `plan/<plan>` by compare-and-swap. A failed run or landing re-queues the task with
the reason, up to three attempts. The first landing pushes `plan/<plan>` and opens the plan's PR against the default
branch via `gh`; later landings update it. When every task has landed, the task worktrees and local task branches
are removed; the integration branch stays, it is the PR. Development runs on the operator's Claude Code login; a
product deployment sets `ANTHROPIC_API_KEY`.

Up to `SESSIONS_MAX` (default 4) phases run at once **across all running plans**: one dispatch pass covers every running plan, file claims are checked across plans within an app (a step with no claims claims the whole app, never another app), and `GET /apps/:id/graph` is the top-level graph with dashed links between open phases that share a file. On startup the server recovers: runs left
`working` are marked `interrupted`, their phases re-queued (the next run resumes the agent's session in the same
worktree), stray `claude` processes inside our worktree roots are stopped, and running plans are dispatched again.
On SIGTERM, live runs are aborted so the agents stop.

`GET /events?since=<seq>&plan=…` is the live feed (SSE): replay from a sequence number, then every committed
event as it happens, via Postgres `LISTEN/NOTIFY`. Several clients can watch one run.

## What's here

| File | Role |
| --- | --- |
| `src/db/schema.ts` | The tables, tagged `[LS]` Lightsprint-derived, `[ID]` InDusk, `[IF]` ours. Prefixed IDs (`task_…`). |
| `drizzle/` | Migrations, generated with `pnpm db:generate` after a schema change. |
| `src/scheduler.ts` | Pure: given a plan's tasks and free slots, what to start and why everything else is held. One pick at a time, so two tasks freed together never claim the same file. |
| `src/plans.ts` | Plans, tasks, phases: create in one transaction, add phases to a task, graphs (plan and app), `tickAll` (one dispatch pass across running plans, task order as implied edges), manual status. |
| `src/planner.ts` | The planner: one read-only Agent SDK run on the repo with the task's brief, ending in one structured proposal (`outputFormat: json_schema`) → phases (brief composed from summary, steps, checks, done-when; files; depends-on), provisional decisions with rejected alternatives, open questions. The server sets each question's cost: an option that changes what was agreed is expensive. |
| `src/events.ts` | Append an event in the same transaction as the state change; `NOTIFY` carries only the seq; readers fetch rows by seq. |
| `src/server.ts` | Hono: `/workspaces`, `/apps`, `/apps/:id/graph`, `/repos`, `/plans`, `/plans/:id/graph`, `/plans/:id/start`, `/plans/:id/tick`, `/tasks/:id/plan`, `/tasks/:id/phases`, `/phases/:id/status`, `/questions/:id/answer`, `/events` (SSE). `GET /` lists them. |
| `src/git.ts` | Worktrees, branches, merge, fast-forward by `update-ref` compare-and-swap, push. |
| `src/executor.ts` | One Agent SDK run on one phase; messages → events (trimmed); the builder's todo list → steps; tools confined to the worktree. |
| `src/landing.ts` | Merge → test → fast-forward, serialized per plan; refuses conflicts and failing tests. |
| `src/pr.ts` | One PR per plan via `gh`, opened at the first landing, updated after each. |
| `src/runner.ts` | Start a plan, dispatch ready phases under the cap across plans, launch, land, retry, keep the PR current, clean up, recover. |
| `src/reap.ts` | Find and stop agent processes working inside our worktree roots (orphans after a crash). |
| `src/cli/if.ts` | The `if` CLI. A client; only `migrate` touches the database. |

`pnpm test` runs the scheduler and landing tests anywhere (landing uses a throwaway git repo) and, when Postgres
is up, the plan, planner and runner tests (a fake proposer; a fake executor on a throwaway repo: the cap, dependents
after parents, two plans at once, retries with the reason, recovery, cleanup) against **their own database**,
`ideafactory_test`, which the global setup creates and migrates (`DATABASE_URL_TEST` to override). The server's
database is never touched.

## Planning

`POST /tasks/:id/plan` (or `pnpm se task plan`) runs the planner on a task that has no phases yet. It reads the
repo at the app's local checkout (nothing is written), gets the task's brief, the plan's title and why, the earlier
tasks (already implied dependencies), and the test command; it returns one object the SDK validates against
`PROPOSAL_SCHEMA`, after one self-review pass in the same run. What it settled is a `decision` (provisional until a
person approves) with the rejected alternatives; what it could not settle is a `question` with options, a
recommendation and what each option changes; the phases go in through `addPhases` like hand-written ones. Progress
is on the event stream (`task.planning`, the run's messages, `question.asked`, `task.planned` or
`task.plan_failed`); the run row of kind `plan` carries cost and the session id. Design: `research/planning-from-indusk.md`.
